### Synthesis of Architectural Recommendations

The objective of extracting highly specific, domain-restricted vocabulary from complex historical Czech texts into a rigid, structured JSON template represents an intersection of advanced NLP challenges: cross-lingual semantic understanding, strict instruction adherence, morphological robustness, and infallible syntactic generation.

Based on an exhaustive analysis of current model benchmarks, localized hardware constraints, and the capabilities of modern inference frameworks, the optimal architecture for resolving the ufal/atrium-nlp-enrich pipeline request involves the deployment of the Qwen 2.5 14B Instruct model. Its extensive pretraining on an unparalleled 36 trillion tokens across 119 languages inherently covers the complex morphology and declensions of the Czech language. Furthermore, its architectural focus on logical reasoning and code synthesis makes it exceptionally reliable for matching unstructured historical text against the hierarchical, nested dictionary structure of the TEATER vocabulary. If computational resources are strictly limited by edge-hardware constraints, the Qwen 2.5 7B or Mistral NeMo 12B provide highly competent operational fallbacks, with Mistral offering a superior 128k context window explicitly designed for massive monolithic document processing and extensive dictionary injections.

Crucially, the ultimate success of this pipeline does not rest on the neural parameters of the LLM alone, but on the absolute enforcement of its output. Relying on traditional prompt engineering to produce JSON is wholly insufficient for automated, high-throughput data systems. The integration of Constrained Decoding—whether implemented through Ollama's native structured outputs or programmatic Python libraries like Outlines—is paramount. By actively masking token logits at the lowest level of the inference engine, the system mathematically guarantees that every response perfectly adheres to the prescribed JSON schema, entirely eliminating the risk of deserialization failures and cyclic repair loops.

When this robust constrained generation is coupled with the dynamic, API-driven ingestion of TEATER GraphQL taxonomy and comprehensive ATRIUM paradata logging, this localized, LLM-driven architecture provides a highly resilient, cost-effective, and fully automated mechanism for the semantic enrichment of archaeological texts.

### Implementation Workflow for ATRIUM NLP Enrichment

To synthesize these neural and architectural components into a functional, production-ready system that definitively resolves GitHub Issue #6, the architecture must seamlessly integrate the ingestion of historical documents, the processing of TEATER API data, and the execution of the local LLM inference engine, while strictly adhering to the ATRIUM project's data governance and structured logging standards.

#### The Inference Pipeline Architecture

**Ingestion and Pre-processing of ALTO Data:**

The pipeline begins by ingesting discrete text lines extracted from the ALTO XML files. This text has already undergone preliminary layout-aware extraction (utilizing architectures like LayoutLMv3) and generative OCR correction (via GLM-4v-9b) to mitigate baseline noise. The language of the text chunk is verified using FastText to ensure it routes to the correct processing logic.Dynamic Vocabulary Injection (Thesaurus Mapping):

The load_vocab.py script actively harvests the relevant TEATER topics, returning the data structure as a nested dictionary of dictionaries. Instead of dumping the entire multi-megabyte thesaurus into the system prompt—which would immediately exhaust the context window and dilute the model's attention, leading to hallucination—the pipeline should utilize semantic similarity search (e.g., using a lightweight embedding model like all-MiniLM-L6-v2). This search retrieves only the top N most relevant TEATER broad and narrow categories for the specific document chunk. These targeted dictionary trees are then dynamically serialized and injected into the system prompt as the permissible keyword list.

**Schema Formulation and Serialization:**
A Pydantic model is defined within the Python runtime, precisely specifying the required output format requested by the user. For example:
```
Pythonclass DocumentEnrichment(BaseModel):
    original_text: str
    extracted_keywords: List[str]
    teater_broad_type: str
    teater_narrow_type: str
    confidence_score: float
```
This class is programmatically serialized into a JSON Schema payload, providing the exact structural blueprint required by the inference engine.

**Inference Execution via Constrained Decoding:**

The designated local LLM (e.g., Qwen 2.5 14B Instruct running via the Ollama execution engine) is invoked. The API request payload includes the input historical text, the dynamically injected TEATER dictionary subset, the system instruction outlining the strict extraction rules, and the generated JSON Schema. The inference engine applies LogitMatch masking, guaranteeing that the generated output perfectly populates the DocumentEnrichment template using only the permitted vocabulary terms.

**Paradata Logging and Provenance Tracking:**

The ATRIUM project places heavy emphasis on data traceability and operational transparency. As the Python script processes the documents, it must generate a unified provenance log. This metadata is saved in a structured JSON format (typically utilizing the naming convention <YYMMDD-HHmmss>_<program>.json within the paradata directory). The paradata captures comprehensive execution details:Provenance: Captures the tool name, repository URL, Python version, and assigns a unique run_id to each discrete execution cycle.

**Configuration**: 

Stores a complete snapshot of the runtime configuration, including input/output directory paths and the specific LLM choice (e.g., qwen2.5-14b-instruct).Timing: Records precise UTC start times, end times, and computes the total duration of the run in seconds to track operational efficiency.Error Tracking: Maintains a highly detailed skipped_files_detail list that logs the exact filename and specific error reason (e.g., token limit exceeded, hardware memory fault, missing ALTO tags) if a file fails to process successfully.

#### Hardware Utilization and Throughput Optimization

Running a robust 14B parameter model locally requires approximately 10GB to 12GB of VRAM when utilizing standard 4-bit quantization (GGUF or AWQ formats). This memory footprint is well within the capabilities of modern consumer GPUs (such as the NVIDIA RTX 3090 or 4090, which feature 24GB of VRAM) or entry-level data center hardware (such as single L4 or A10g instances).To maximize throughput for bulk historical document processing, the pipeline should deploy the model using an inference engine optimized for continuous batching, such as vLLM. While standard Ollama provides unparalleled ease of use and native JSON schema integration for rapid deployment, vLLM allows multiple text chunks to be processed in parallel, maximizing GPU utilization. Metrics derived from generating high-quality Czech texts on the LUMI-G supercomputer indicate that optimized local inference can achieve throughputs of approximately 250 to 300 input tokens per second and 150 to 170 output tokens per second, ensuring that massive archives of ALTO XML files can be enriched rapidly and cost-effectively.

## EXTRA: LLM Semantic Enrichment (Vocabulary Mapping)

> [!NOTE]
> This is an advanced, optional step. It utilizes a local Large Language Model (LLM) through Ollama to semantically analyze text lines and rigidly map them to a nested, controlled archaeological vocabulary (e.g., TEATER or AMCR).

This pipeline goes beyond traditional keyword extraction by using **Constrained Decoding** (via Pydantic schemas). This mathematically guarantees that the LLM only outputs valid JSON structures and exclusively uses permitted terms from the injected hierarchical dictionary, entirely eliminating hallucinated formatting.

### ⚙️ Configuration (`llm_config.txt`)

The pipeline reads its runtime parameters from a plain text configuration file placed in the repository root. This allows you to easily swap the underlying LLM (e.g., `qwen2.5:14b-instruct` or `mistral-nemo`) depending on your local hardware capabilities.

```text
MODEL_NAME=qwen2.5:14b-instruct
OLLAMA_HOST=http://localhost:11434
INPUT_DIR=data_samples/DOC_LINE_LANG_CLASS
OUTPUT_DIR=data_samples/KW_PER_DOC
VOCAB_PATH=data_samples/teater_nested_vocab.json
PARADATA_DIR=paradata
LLM_TEMPERATURE=0.0
```

### 🗂 Workflow 

**1. Vocabulary Harvesting (`vocab_manager.py`)**
Before running the inference, the system must build the allowable vocabulary list. The vocabulary manager actively queries upstream APIs (via HTTP GET requests with XML pagination) to fetch Czech-English term pairs. It then structures them into a nested JSON taxonomy and caches it locally (`teater_nested_vocab.json`) to prevent exhausting the LLM's context window.
```bash
python3 vocab_manager.py
```

**2. LLM Inference Pipeline (`llm_pipeline.py`)**
This script reads the page and line-ordered text chunks from the CSV files in `DOC_LINE_LANG_CLASS`, injects the nested vocabulary into the system prompt, and executes the LLM generation. 
```bash
python3 llm_pipeline.py
```

### 📁 Inputs and Outputs

* **Input:** `DOC_LINE_LANG_CLASS/*.csv` (Contains `file_id`, `page`, `line`, and raw `text`).
* **Output:** `KW_PER_DOC/*_enriched.json` (An array of highly structured JSON objects securely merging the deterministic CSV metadata with the LLM's semantic extraction).

**Example Output Record:**
```json
{
  "file_id": "CTX195603828",
  "page": 1,
  "line": 14,
  "original_text": "Výzkum odhalil základy gotického kostela ze 14. století.",
  "enrichment": {
    "extracted_keywords_cs": ["základy", "gotický kostel"],
    "extracted_keywords_en": ["foundations", "gothic church"],
    "teater_broad_category": "Architecture (Architektura)",
    "teater_narrow_category": "Church (Kostel)",
    "confidence_score": 0.95
  }
}
```

### 📊 Paradata Integration

Just like the main shell script pipelines, the LLM enrichment natively hooks into `atrium_paradata.py`. It automatically logs:
* Full snapshot of `llm_config.txt`.
* Total processed lines (`json` success events).
* Line-level tracking of skipped entities (e.g., if a specific text line triggered an LLM inference fault or was unreadable).
The resulting log is dropped into `<OUTPUT_DIR>/paradata/` alongside the other pipeline execution records.

Based on an analysis of the semantic enrichment results across the 6 LLMs for the ATRIUM archaeological documents, here is a comprehensive evaluation of the current pipeline's performance.

### **Model Comparison & Evaluation**

#### **1. Qwen 2.5-14b-AWQ (The Gold Standard)**
* **Strengths:** This model is the most consistent and accurate. It correctly maps metadata lines (headers, table of contents) to administrative categories like `nálezová zpráva` or `zprávy a hlášení`. It shows a nuanced understanding of archaeological context, distinguishing between specific architectural features (`hradba`, `objekt`) and broader site types.
* **Weaknesses:** High resource requirements (AWQ 14b).
* **Confidence:** High and justified (usually 0.95–1.0).

#### **2. Qwen 2.5-7b**
* **Strengths:** Performance is very close to its 14b sibling but with slightly lower confidence scores. It maintains good keyword extraction quality.
* **Weaknesses:** Occasionally less precise in category selection compared to the 14b version, sometimes opting for more generic terms.
* **Confidence:** Balanced (0.85–0.95).

#### **3. Mistral Nemo 12b**
* **Strengths:** Very robust keyword extraction; the "Extracted Keywords" list is often comprehensive.
* **Weaknesses:** **Aggressive Over-generalization.** It has a strong bias toward the category `hradiště` (hillfort), applying it to almost every line including headers, metadata, and general descriptions where it doesn't strictly belong.
* **Confidence:** Misleadingly high (1.0) even when the categorization is repetitive or questionable.

#### **4. Bielik 11b**
* **Strengths:** Excellent at identifying very specific chronological and site sub-types (e.g., `rané středohradištní období`) when the text provides enough detail.
* **Weaknesses:** **"The Country Default" issue.** When encountering lines it cannot easily categorize (like "Obsah" or "Literatura"), it defaults to picking country names (e.g., `Dánsko`, `Džibutsko`, `Litva`) from the "Other" category in the vocabulary.
* **Confidence:** Binary behavior—either 0.99 for specific matches or 0.0 when it defaults to country names.

#### **5. Llama 3.1-8b**
* **Strengths:** Decent keyword extraction and a varied vocabulary usage.
* **Weaknesses:** Similar to Bielik, it suffers from defaulting to irrelevant "Other" categories like country names (`Finsko`, `Dominika`) for meta-text. It often struggles with low-quality or short lines, resulting in `neurčený areál`.
* **Confidence:** Generally lower and more erratic (0.5–0.8).

#### **6. Aya Expanse 8b**
* **Strengths:** Unique perspective; it often identifies the role of the person mentioned in the text (categorizing headers as `archeolog`).
* **Weaknesses:** Categorization is often "outside the box" in a way that doesn't align well with the intended TEATER vocabulary mapping. English keywords are frequently just copies of the Czech terms.
* **Confidence:** Consistently around 0.95.

### **Identified Areas for Improvement**

1.  **Vocabulary Filtering for Constrained Output:**
    * The `build_schema` function in `llm_pipeline.py` currently includes all 1000+ terms in a single `TermEnum`.
    * **Improvement:** Exclude the "Other" (countries/languages) category from the dynamic schema when processing certain line types to prevent models from defaulting to `Dánsko` or `Zimbabwe` for metadata.

2.  **Context Window Optimization:**
    * The current window of 2 lines is helpful but sometimes insufficient for complex structures.
    * **Improvement:** Implement a "Section Detection" mechanism where the LLM is informed of the current document section (e.g., "History," "Description of Finds") to improve thematic mapping consistency.

3.  **Handling of Noisy/Short Lines:**
    * Models currently try to force a category onto lines like "Práce:" or "Obsah:".
    * **Improvement:** Explicitly allow a `None` or `Meta-text` category in the vocabulary to prevent hallucinated high-confidence mappings for non-semantic lines.

4.  **Model Selection Strategy:**
    * **Recommendation:** Use **Qwen 2.5-14b-AWQ** for high-precision batch processing. If resources are limited, **Qwen 2.5-7b** offers the best performance-to-cost ratio while avoiding the "country default" traps of Llama and Bielik.

### 1. Code Changes & Logic Updates
The current code successfully integrates the targeted improvements to solve previous hallucinations and context amnesia:

* **Explicit Meta-Text Fallback:** In `llm_pipeline.py` (`build_system_prompt`), a dedicated category `"Nerelevantní (meta-text)"` is now injected at index `0`. The code ensures this term always survives context-window truncation. The Pydantic schema description explicitly instructs the model to use this for "headers, footers, table of contents, or any line lacking direct archaeological significance."
* **Thematic Capping:** The noisy "Other" category (which previously caused models to hallucinate country names) is now strictly capped to 15 terms in the prompt builder (`build_candidate_prompt`), drastically reducing the probability of models picking random geographical terms.
* **Global Document Context Injection:** The `get_context_window` function now implements a `GLOBAL DOCUMENT HEADER`. For any line processed beyond the first few lines of the document, the script prepends the first two non-noise lines of the entire document. This successfully anchors the LLM by reminding it of the core subject (e.g., "Výzkum slovanského hradiště") even when processing page 15 of a report.
* **Translation Hinting:** The Pydantic `ConstrainedEnrichment` schema now includes explicit directions for `extracted_keywords_en`: *"Do not copy the Czech words unchanged"*, aiming to fix the lazy translation issue observed in some models.

### 2. Taxonomy & Vocabulary Changes
* **Thematic Grouping:** The vocabulary has shifted from a flat dictionary to a nested structure (`teater_nested_vocab.json`), categorized by broad archaeological domains: `"Site Types"`, `"Find Types"`, `"Methods"`, `"Chronology"`, `"Location & Admin"`, `"Documentation"`, and `"Finds Context"`. 
* **Prioritization:** The new `taxonomy_config.json` assigns weights/priorities to these themes (e.g., Chronology = 9, Site Types = 8). The prompt builder sorts terms using a custom `_term_priority` logic to ensure the most highly relevant terms appear first in the prompt, guaranteeing they aren't cut if the token window limit is reached.

**Defining a new set of models fit for this task is the immediate priority.** To maintain operational throughput and pipeline stability, we propose standardizing on a highly optimized triad of sub-15 billion parameter models:

* **Qwen 3 14B (Multilingual Powerhouse):** Highly resilient to ALTO XML OCR noise due to deep, document-level multilingual pre-training. *Crucial Implementation Note: This must be instantiated in "Non-Thinking Mode" to ensure pure JSON output, as chain-of-thought `<think>` tags will break the constrained decoder.*
* **Bielik 11B v3.0 (Regional Specialist):** A Central European language specialist that dominates Czech NLP benchmarks (BenCzechMark). It utilizes a customized tokenizer designed specifically for Czech diacritics and roots, ensuring the highest accuracy when categorizing and translating highly localized historical terminology.

### 2. Key Performance Dimensions

#### A. Meta-text Filtering (Signal vs. Noise)
Archaeological reports contain a lot of administrative boilerplate (dates, authors, locations like "v Praze dne 6.října 1956"). For an archive, indexing "October" or "Dr. Solle" as a *topic* keyword dilutes search quality.
* **The Best Approach (`gemma_4_31b_it`):** This model correctly identifies administrative lines, classifies them strictly as `Nerelevantní (meta-text)`, and **leaves the keyword arrays empty** (`[]`). This prevents index bloat.
* **The Noisy Approach (`gemma_3_12b_it`, `qwen_35_9b_it`):** These models correctly classify the line as `Nerelevantní (meta-text)` but still extract keywords like "Praha", "6.října", and "Vojáček". This requires downstream filtering in your pipeline to ignore keywords if the category is irrelevant.

#### B. OCR Error Resilience & Normalization
Archival documents scanned via ALTO/OCR often contain typos (e.g., "LÁzE" instead of "jáma", "konsttukcí" instead of "konstrukci").
* **`gemma_4_31b_it` and `qwen_36_27b_it`** show excellent semantic understanding. For the text `"úpravy. Z nejstarší fáse pocházejí 3 hluboké zásobní LÁzE j ámy"`, they dynamically correct the text in their output, extracting **"hluboké zásobní jámy"** (Gemma) or **"zásobní jámy"** (Qwen 36B).
* **Smaller models** blindly extract the OCR garbage directly (e.g., extracting "LÁzE", "j ámy").

#### C. Severe Failure Mode: Repetitive Looping
The smaller Qwen models completely fail at handling complex line structures, falling into infinite concatenation loops. 
* Look at **`qwen25_7b`** and **`qwen3_8b`** on Line 24. They output arrays filled with exponentially growing strings:
    * `"zásobní LÁzE j ámy zásobní jámy"`
    * `"zásobní jámy j ámy zásobní LÁzE j ámy zásobní jámy j ámy zásobní jámy"`
    * *...and so on until the token limit.*
* *Conclusion:* These models must be immediately excluded from the pipeline as they will corrupt your Elasticsearch/database indices with massive garbage strings.

#### D. TEATER Vocabulary Adherence (Categorization)
The models are tasked with assigning a `teater_category` to each line.
* **Accurate Mapping (`qwen_36_27b_it`, `gemma_3_12b_it`):** These models accurately map lines to standard, recognizable archaeological terms: `ohrazení/fortifikace` (fortifications), `sídliště` (settlements), `jáma zásobní` (storage pits), and `pohřebiště/hřbitov` (cemeteries).
* **Over-specificity (`qwen25_14b_awq`):** This model invents or uses overly specific categories that might not exist in your root TEATER taxonomy, such as `ohrazení polygonální střední`. (Check your `taxonomy_config.json` to see if this is allowed; if not, the model is hallucinating sub-classes).
* **Complete Hallucination (`qwen3_14b`):** On line 14, which discusses wooden and stone rampart constructions, this model inexplicably assigns the category **`metalografie`** (metallography) and **`objekt/stopa výroby`** (production trace). It completely lacks domain context.

## `llm_run.py` — Pipeline Entry Point

This is the **main script** you run to kick off the enrichment process. Here's what it does, in order:

1. **Reads config** from `llm_config.txt` (paths, model name, filtering thresholds, etc.)
2. **Loads a thematic vocabulary** (Czech/English archaeological terms from a JSON file) and builds a system prompt that embeds it
3. **Builds a constrained Pydantic schema** using the vocabulary terms as an Enum — this forces the LLM to only ever output a valid category name (no hallucinated labels)
4. **Loads the LLM** (model + tokenizer) via `llm_utils`
5. **Loops over every `.csv` file** in the input directory, calls `process_document()` on each, and writes the results as JSON files in the output directory
6. **Logs run metadata** (successes, skips, errors) via a `ParadataLogger`

---

## `llm_utils.py` — Shared Utilities Library

This module contains all the **reusable building blocks** imported by `llm_run.py`. Key components:

| Section | What it does |
|---|---|
| **CUDA guard** | Sets `PYTORCH_CUDA_ALLOC_CONF` before any GPU library loads — must be the very first import |
| **Compatibility shims** | Patches `bitsandbytes` and `transformers` version mismatches at runtime (e.g., 4-bit quantization bugs with MoE models) |
| **Model Registry** | A dictionary of supported models (Gemma, Qwen variants) with their HuggingFace IDs, context window sizes, and quantization settings |
| **`load_config()`** | Parses a simple `KEY=VALUE` text config file |
| **`load_model_and_tokenizer()`** | Loads a model by registry key — handles both GGUF (via `llama.cpp`) and standard Transformers models with optional 4-bit quantization |
| **`_should_process_line()`** | Filters out rows before inference: skips empty lines, noise categories, very short text, or non-text with too few alphabetic characters |
| **`get_context_window()`** | Builds the LLM user prompt for a given line by surrounding it with ±2 neighbouring lines and a global document header for context |
| **`process_document()`** | The core inference loop — iterates over rows in a CSV, runs the LLM on each qualifying line, parses/validates the JSON output, and returns enriched results |

### In plain terms

This codebase takes **CSV files of text lines extracted from archaeological documents** (likely OCR'd scans), feeds each line to a large language model with a Czech/English thematic vocabulary, and asks the model to:
- extract relevant **Czech archaeological keywords** from the line
- translate them to **English**
- assign it a **single category** from the vocabulary
- give a **confidence score**

The output is a structured JSON file per document, ready for downstream analysis or indexing.

### **Detailed Comparison of Findings**

#### **1. Handling of OCR Noise & Meta-text**
The primary differentiator between the models is their ability to ignore "uninformative" text.
* **Gemma 4 31B** and **Qwen 3.6 27B** consistently used a 1.0 confidence score for `Nerelevantní (meta-text)` on headers like "Věc : Stará Kouřim".
* **Qwen 3 14B** and **Gemma 3 12B** frequently hallucinated archaeological relevance for these lines, categorizing them as `hradiště` or `ohrazení`, which pollutes the final statistics.

#### **2. Keyword Quality & Translation**
* **Top Performers (Gemma 4 / Qwen 3.6):** These models extract contextually relevant phrases (e.g., `slovanské hradiště` -> `Slavic hillfort`) and avoid simple word-for-word repetition.
* **Legacy/Lower Tier:** Some models (like the archived Aya Expanse or Bielik 11b) struggled with the instruction "Do not copy the Czech words unchanged into English".

#### **3. Constraint Adherence**
Unlike older archived models (like **Bielik 11b**) which suffered from catastrophic "repetition loops" (20x copies of the same word), all 6 models in the current run adhered to the Pydantic JSON schema without crashing the `lmformatenforcer`.

### **Recommendation for Production**
Based on the results for document `CTX201601688`, the project should standardize on **Gemma 4 31B Dense** or **Qwen 3.6 27B Dense**. For hardware-constrained environments (under 16GB VRAM), **Qwen 3.5 9B** is the recommended alternative to ensure pipeline stability.

#### `llm_utils.py`

- **Remove `PYTORCH_CUDA_ALLOC_CONF` env-var guard** — vLLM manages physical VRAM allocation
  internally via PagedAttention; the `expandable_segments` workaround is only needed because the
  `transformers` inference loop fragments memory.

- **Remove the `PreTrainedTokenizerBase` compatibility shim** (lines 31–33) — the shim patches a
  `transformers` 5.x dev regression; it is dead code once `transformers` is no longer used for
  inference. vLLM bundles its own tokenization path and does not import
  `transformers.tokenization_utils` at runtime.

- **Remove `_patch_params4bit_compat()`** — the entire bitsandbytes shim becomes dead code once
  on-the-fly BnB 4-bit quantization is dropped in favour of pre-quantized AWQ/GGUF weights.

- **Remove `_verify_quantization_effective()`** — only relevant for BnB runtime quantization;
  pre-quantized models have a fixed, known footprint.

- **Replace `AutoModelForCausalLM` / AWQ loading blocks with `vllm.AsyncLLMEngine`** — initialize
  with `tensor_parallel_size=2`, `enable_prefix_caching=True`, `gpu_memory_utilization=0.95`,
  `guided_decoding_backend="xgrammar"`. This also changes the **signature of
  `load_model_and_tokenizer()`**: the function currently returns a `(model, tokenizer, spec)`
  tuple; under vLLM it should return `(engine, spec)` — there is no separate tokenizer object
  to thread through the codebase, as vLLM handles tokenization internally.

- **Remove the `count_tokens()` helper** — token counting for binary-search truncation is no
  longer needed once the full vocabulary is always injected; keep only if used elsewhere.

- **Remove or stub out `process_document()`** — its sequential `model.generate()` loop is
  incompatible with vLLM's async batch scheduler; replace with an async generator that pushes
  `SamplingParams`-wrapped requests to the engine.  
  The Qwen3-specific thinking-mode suppression currently inlined in `process_document()`
  (`is_qwen3` detection, `/no_think` suffix, `enable_thinking=False` in `apply_chat_template`)
  must also be removed from here; under vLLM this is handled once at engine init time via the
  model's chat template configuration or a model-level `SamplingParams` default — not per
  request inside the processing loop.

- **Fix silent mid-document abort** — when `consecutive_errors >= 10` triggers, write an explicit
  `"aborted": true` flag into the output JSON so downstream consumers know the document is
  partial, rather than silently stopping.

- **Harden `_should_process_line()`** — currently a no-op for `categ == ""` (empty string after
  `.strip()`); add an explicit guard so lines with missing category metadata are logged as
  skipped rather than passed through as if they were valid text:
  ```python
  if not categ:
      return False, "missing categ metadata"
  ```

---

#### `llm_run.py`

- **Remove `lmformatenforcer` imports entirely** — `JsonSchemaParser` and
  `build_transformers_prefix_allowed_tokens_fn` are both `lmformatenforcer`-specific and have no
  vLLM equivalent. Under xgrammar + vLLM, the constrained output contract is expressed as:
  ```python
  from vllm.sampling_params import GuidedDecodingParams

  SamplingParams(guided_decoding=GuidedDecodingParams(json=EnrichmentModel.model_json_schema()))
  ```
  The `parser = JsonSchemaParser(...)` and `prefix_function = build_transformers_prefix_allowed_tokens_fn(...)`
  block in `main()` should be replaced with a single `guided_params` object constructed once and
  reused per request. `build_schema()` itself can be kept as-is since it still produces the
  Pydantic model whose `.model_json_schema()` is passed to `GuidedDecodingParams`.

- **Remove the `import llm_utils  # noqa: F401` side-effect import** at the top of the file —
  it currently exists solely for its side effects (`PYTORCH_CUDA_ALLOC_CONF` guard +
  `_patch_params4bit_compat()` call). Once both are removed from `llm_utils.py`, this import
  reverts to a normal functional import with no ordering constraint.

- **Remove vocabulary truncation entirely** — delete the `while lo < hi - 1` binary-search block
  inside `build_system_prompt()`; on 100 B+ models with 128 k–262 k context windows the full
  AMCR vocabulary (~15 k–25 k tokens) fits comfortably.

- **Remove `other_cap=15` in `_build_candidate_prompt()`** — the hard cap that silently truncates
  "Other" theme terms to 15 entries was only justified when the vocabulary might overflow the
  context budget. With full vocabulary always injected the cap becomes dead code and would
  silently hide valid AMCR terms; remove it or replace with `len(other_terms)` (no cap):
  ```python
  # Before
  prompt += "\n".join(f"- {t['cs']} ({t['en']})" for t in other_terms[:other_cap]) + "\n"
  # After
  prompt += "\n".join(f"- {t['cs']} ({t['en']})" for t in other_terms) + "\n"
  ```

- **Invert the prompt structure** — move the static tiers (system instructions → output schema →
  full serialized vocabulary → few-shot examples) to the absolute beginning of the context
  string, and append the dynamic `<target_line>` payload at the very end; any dynamic content
  before the vocabulary block breaks the APC hash chain at token 0 and yields a 0 % cache hit
  rate on the 20 k-token prefix.

- **Replace blocking `process_document()` calls with async dispatch** — read all target lines
  from input CSVs upfront, push them to the vLLM engine via `engine.generate()` concurrently,
  and collect results; this lets the engine's continuous-batching scheduler overlap prefill and
  decode phases across multiple requests, saturating both GPUs.

- **Migrate paradata logger calls into the async result collector** — the current synchronous
  `for csv_file in csv_files:` loop calls `logger.log_document_success()` / `logger.log_skip()`
  directly inside the loop body. Under async dispatch these calls must move into the coroutine
  that collects completed engine results, otherwise the logger sees all documents as either
  succeeded or not-yet-started until the entire batch drains.

- **Remove `torch.cuda.empty_cache()` from the `finally` block** — unnecessary and
  counterproductive inside vLLM, which manages its own KV-cache block lifecycle.

- **Update the model registry entries** — for 100 B+ candidates, add
  `"vllm_tensor_parallel": 2`; remove `load_in_4bit`, `bnb_experts_broken`, and AWQ-specific
  flags that are only needed for the `transformers`/`autoawq` path; keep GGUF entries as a
  fallback but flag them as incompatible with the new async path. Remove `torch_dtype` fields
  from non-GGUF entries — under vLLM the dtype is specified at engine init
  (`dtype="bfloat16"` in `AsyncLLMEngine`), not per registry entry.

#### `vocab_manager.py`

- **Add `sort_keys=True` to `get_prompt_string()`** — Python dict ordering is insertion-ordered
  but not formally guaranteed to be identical across runs or worker processes; without
  deterministic byte-level output the vLLM APC hash chain can silently miss on an otherwise
  identical vocabulary block:
  ```python
  return json.dumps(self.vocab_data, indent=2, ensure_ascii=False, sort_keys=True)
  ```

- **Refactor `_assign_theme()` fallback** — the hardcoded `_arch_keywords` / `_arch_prefixes`
  exclusion lists in `_term_priority()` (in `llm_run.py`) will drift out of sync as the taxonomy
  grows; move the priority rules into `taxonomy_config.json` as an explicit `"priority"` field
  per theme so they are data-driven and version-controlled alongside the vocabulary itself.

- **Cache the serialized prompt string** — `get_prompt_string()` re-serializes the entire nested
  dict on every call; memoize the result (e.g. with `functools.lru_cache` or a simple instance
  attribute) so the first vLLM request pays the serialization cost and all subsequent ones reuse
  the identical string, which is also what guarantees the APC prefix hash stays constant across
  the whole run.

#### `llm_config.txt`

#### Cross-cutting

### Bug fixes (Issue #6, items 7 & 8)

**Bug #7 — Silent abort with no marker written**
Previously, when a document hit 10 consecutive errors, the loop broke silently. If there were partial results they were written without any indication of incompleteness; if there were none, the document was logged as a generic skip with no abort reason. **Bug #8 — Empty `categ` string passes through unguarded**
In `_should_process_line`, an empty string `categ=""` fell through every category guard silently, hitting only the `min_char_count` check. ### vLLM backend (Issue #6, items 2 & 3)

**`load_vllm_engine()` in `llm_utils.py`** loads any registry model via vLLM with:
- `tensor_parallel_size` — shards the model across N GPUs automatically, no manual pipeline cuts needed
- `enable_prefix_caching=True` — Automatic Prefix Caching (APC): the system prompt (which embeds the full vocabulary) is computed once and its KV-cache is reused for every line in every document. This is the primary throughput multiplier for this pipeline.
- `guided_decoding_backend="xgrammar"` — native constrained JSON decoding, no lmformatenforcer needed
- `tokenizer_pool_size` — parallel tokenizer threads, scaled to `tensor_parallel_size`

**`process_document_vllm()` in `llm_utils.py`** replaces the one-at-a-time inference loop with mini-batch processing: all qualifying lines are filtered upfront, chat prompts are formatted, then submitted to `llm_engine.generate()` in configurable batches (`VLLM_BATCH_SIZE`). Consecutive-error abort logic is preserved, evaluated after each mini-batch.

**`llm_run.py` dispatch** reads `BACKEND=` from config and routes to either path. With `BACKEND=vllm` and `ENABLE_PREFIX_CACHING=true`, `build_system_prompt()` skips token-budget truncation entirely — injecting the full vocabulary is effectively free when the KV-cache is shared (Issue #6, item 4). lmformatenforcer is only imported when `BACKEND=transformers`.

#### Rankings and findings

**Gemma 4-31B (100%)** is the clear winner on this sample. It never bleeds context across lines, handles ambiguous abbreviations conservatively, consistently picks the most specific TEATER term ("zlomek keramiky" over "keramika", "pohřeb kostrový" over "hrob"), and gives 1.0 confidence only on genuine meta-text. Its only tradeoff is needing ~21 GB VRAM and a gated HF token.

**Qwen 3.6-27B (94%)** — the current default — is the right default choice. Its single deduction is `sklep` (cellar) where `jáma zásobní` (storage pit) would be more precise for the krechty context. Every other decision is correct, including resisting the temptation to guess a culture from the ambiguous "Kultura Z." abbreviation.

**Qwen 3.5-9B (81%)** punches well above its weight class. Zero context bleeding, correctly conservative on ambiguous inputs, just slightly imprecise on burial and storage-pit categorisation. Strong candidate for CPU/low-VRAM deployments.

**Qwen 3-14B (75%)** is solid but has a notable context-bleed pattern on CTX199405706: both line 3 (a bare location header) and line 26 (an introductory sentence) get classified using vocabulary from the *next* content line. This suggests the model's sliding-window context is influencing classification slightly beyond the current token boundary.

**Qwen 2.5-14B AWQ (62%)** — the worst hallucination in the evaluated set occurs here: the intro sentence "P.Jirušek starousedlík… informaci že před" is assigned `kultovní/sakrální objekt` at confidence 0.75 with no archaeological basis whatsoever. Also misassigns `jáma zásobní` to line 28 (the sherds-found line) after correctly assigning it to line 27, suggesting it's tracking the previous output rather than the current input.

**LLaMA 3.1-70B (53%)** has the highest hallucination count despite being the largest evaluated model. It invents `cihla` (brick) for "ČÍSLO PARCELY", maps the standalone word "OBEC" to `sídliště`, and assigns `vrcholný středověk–novověk` (with confidence 0.0, which is at least honest) to a hill-name line. The 0.0 confidence on one line suggests the model has some epistemic self-awareness, but the hallucinations on meta-text fields are a practical problem for a pipeline that processes thousands of form-structured records.

**Gemma 3-12B (47%)** has a systematic context-bleeding problem: it consistently imports vocabulary from the *following* line into the current line's classification. "Druh nálezu" (form label for "type of find") becomes `keramika` because the next line contains ceramic sherds. The same pattern appears on the intro sentence for CTX197901442 and on the location header for CTX199405706. This is the most consistent failure mode in the set.

**Qwen 3-8B (28%)** is the weakest evaluated model. Four context-bleeding events, overconfident wrong culture assignment (0.95 on the wrong culture for "Kultura Z."), and a qualitatively different failure on CTX199405706 line 5 where it assigns `pohřební objekt` (burial) to a line about pottery kilns — the burial from the previous line completely dominates. The README's archived "early run" of this model presumably showed similar or worse behaviour, and the later run shown here doesn't redeem it sufficiently for production use.

#### Patterns that predict failure

The three litmus tests are good proxies for general reliability:

**Form labels as content** ("Druh nálezu") — three models fail (Gemma 3-12B, Qwen 2.5-14B AWQ, Qwen 3-8B). This is the most practically damaging error since archaeological card files are heavily form-structured; misclassifying field names pollutes the enrichment output at scale.

**Ambiguous abbreviations** ("Kultura Z.") — four models make a confident wrong guess. The correct answer is uncertainty (Nerelevantní), not a committed archaeological culture. Models that fail here are likely to over-classify other abbreviated or partial tokens throughout a collection.

**Location headers** (CTX199405706 line 3) — four models assign it a content category drawn from an adjacent line. This is a sliding-window artefact: the model is seeing the header + subsequent content lines as a unit and letting the content pull the header's classification.

#### Note on archived models

The README marks Mistral Nemo 12B, Aya Expanse 8B, Bielik 11B v3.0, LLaMA 3.1-8B, Ministral 3-14B, the early Qwen 3-8B run, and Qwen 2.5-7B as archived/unsuccessful. The pattern from the evaluated set is consistent with why: smaller or non-Czech-specialized models produce higher context-bleeding and culture-confusion rates, and the 7B class appears to be below the capability threshold for reliable constrained JSON + TEATER vocabulary adherence at this task complexity. The current Qwen 3-8B result (28%) confirms 8B is the bottom boundary even in the best case.

#### Practical recommendation

For production: **Qwen 3.6-27B** (default) is the right balance — it avoids all bleeding and hallucination, fits on a single A100/A40, and the single imprecision (sklep vs. jáma zásobní) is arguably recoverable at post-processing. **Gemma 4-31B** is worth the extra VRAM if you need maximum precision on burial and find-type categorisation. For resource-constrained nodes, **Qwen 3.5-9B** is the only sub-14B model that doesn't exhibit context bleeding on this sample.

In general, the source vocabularies should remain authoritative in how their terms are organised and interpreted. In particular, AMCR vocabulary is relatively stable and changes to it can have a wide impact across the infrastructure, so issues such as "`kostel`, `kaple`, `mlýn` and `cesta` landed in `Activity Area`" should not be opened and resolved within this workflow. This task should be about applying the vocabularies, not reorganising them. Any actual change to the AMCR vocabulary needs a dedicated decision process and consideration of all related impacts. TEATER may be somewhat less stable in this respect, but again, it is not for ATRIUM to redefine its vocabulary structure.

At the same time, I am not sure how much the facet assigned to a particular term actually matters here. The main objective is to understand the semantics of the document and link it to the appropriate controlled term. If facets are primarily an internal mechanism for organising/prioritising the prompt, rather than part of the semantic output, I would distinguish clearly between **which terms are available to the model** and **how those terms are grouped for inference**. The latter should not be treated as a new authoritative taxonomy. If the full vocabulary fits into the model context, it may also be worth checking empirically how much facet placement affects the results at all.

From that perspective, excluding parts of the TEATER vocabulary is possible, but I would not do so without a good reason. The purpose of this task/tool is to produce grounded and useful semantic keywords, so it would be a pity to discard parts of a high-quality domain vocabulary that may help describe our documents. I would exclude branches primarily on the basis of evidence from the enrichment results — for example, if they prove irrelevant for the intended content description or introduce systematic and otherwise unsolvable bias/noise.

For AMCR, however, there are several vocabularies that are purely technical or administrative and have little practical value for semantic content description. I therefore agree that most of what is currently grouped under the `Documentation` facet can be excluded. Of the remaining lists, `udalost_typ` still seems potentially useful. ### Summary of recent decisions

**Vocabulary creation**
- Source vocabularies (AMCR, TEATER) stay authoritative — this task *applies* them, it does not reorganize them.
- Facets are internal prompt-organization/prioritization only, not a new semantic taxonomy; keep "which terms are available" separate from "how they're grouped."
- Default is keep; exclude TEATER content only on evidence from results, not a priori. AMCR's purely technical/administrative lists (`dokument_*` etc.) are excluded; `udalost_typ` is kept.
- `Documentation` facet dissolves (only `udalost_typ` left) → folded into `Location & Admin` as an implementation detail, not a reclassification.
- Dedup: list all discarded record ids on the surviving term (drop later if it causes issues). Genuine homonym collisions (e.g. `zámek` = lock vs. château) get a bracketed qualifier, per the convention both sources already use.
- **Open**: terms where two labels denote the same concept (`most` vs. `most/brod`) — no rule yet, to be proposed from the data.

**LLM system prompt**
- Static tiers (instructions → schema → vocabulary → few-shot) first, dynamic target line last, to preserve prefix-cache hits.
- `Nerelevantní (meta-text)` injected at index 0, protected from truncation.
- Temperature 0; explicit preference for the most specific matching term.
- Facet order is priority-descending and load-bearing (truncation drops a *suffix*) — not to be alphabetized/sorted.
- Geographic guardrail (no country/region as primary category) — needs reconciling now that some TEATER branches with place/ethnic terms may be reinstated; **unresolved**.

**JSON output standard**
- Constrained decoding (Pydantic schema → xgrammar) guarantees schema-valid output; no free-form categories.
- Fields: `extracted_keywords_cs`, `extracted_keywords_en`, `teater_category`, `confidence_score`.
- Keyword arrays forced empty when category is `Nerelevantní (meta-text)`.
- Planned addition: attach surviving-term's discarded-id set to output (e.g. `teater_category_ids`); bracketed qualifiers are prompt-only and stripped from the emitted keyword.
