## 🎯 Goal

Make `atrium-keyword-extract` the single current owner of the ATRIUM **keyword stage**:

- statistical keyword extraction: **KeyBERT** by default, **YAKE** selectable, **KER/legacy** retained;
- controlled vocabulary keyword extraction: the local/inference-server LLM over AMČR and TEATER vocabularies;
- one service surface, **`POST /extract_keywords`**, with `kind=statistical|controlled|both`;
- document-level and per-page keyword output;
- every keyword carrying its **method, score and rank**;
- statistical and controlled keywords staying separate;
- controlled enrichment / entity links becoming the successor of the former `llm-enrich` record ownership;
- the new record-level `keywords` block being owned by `keyword-extract` under [atrium-project#73](https://github.com/ufal/atrium-project/issues/73);
- every successful run carrying the shared Process Run Crate `CreateAction` / `paradata` contract from [atrium-project#71](https://github.com/ufal/atrium-project/issues/71).

The repository split is therefore no longer the primary work. The issue is now the **completion and production hardening of the new keyword stage**.

## ✅ What's settled

### Repository and naming

- Current repository: **`ufal/atrium-keyword-extract`**.
- Current service id: **`atrium-keyword-extract`**.
- Current program id: **`keyword-extract`**.
- Do not use `atrium-keyword-extractor` as the production repository/service identity.
- `v1.0.0-beta` is the first released snapshot of the new repository and remains the historical migration baseline.

### Functional boundary

`keyword-extract` owns:

- KeyBERT;
- YAKE;
- legacy KER;
- controlled AMČR/TEATER vocabulary extraction once integrated;
- entity links produced by the former controlled-enrichment stage;
- the future record `keywords` block.

`keyword-extract` does **not** own:

- UDPipe / NameTag;
- TEITOK as a second independent writer;
- born-digital conversion;
- page classification;
- OCR quality categorisation;
- translation.

### Statistical keyword contract

The released service already defines the usable statistical baseline:

```text
POST /extract_keywords
    document_json + kind + method + num_keywords + lang + per_page
        ↓
    document + per-page keywords
    each keyword: method + score + rank
    + kinds status
    + paradata.CreateAction
    + limits_applied
```

The current methods are:

| Method    | Current status | Runtime / score                                               |
|-----------|----------------|---------------------------------------------------------------|
| `keybert` | ✅ default      | embedding-based; cosine score in `[0, 1]`; GPU when available |
| `yake`    | ✅ selectable   | CPU; normalised inverse YAKE score in `[0, 1]`                |
| `legacy`  | ✅ selectable   | KER lemma count; requires `lines[].lemma` / `lines[].upos`    |

Scores are not cross-method comparable; the method field and rank are part of the contract.

### Controlled keyword direction

The controlled kind stays separate from statistical extraction:

- input is the same record;
- vocabulary comes from AMČR + TEATER;
- output includes Czech/English keyword labels and thematic category information;
- entity links to AMČR/AAT remain part of the successor behaviour;
- constrained JSON generation is the intended contract;
- the production API should become a **client of the approved inference service**, rather than shipping full LLM weights inside the statistical `-api` image;
- the current research `-llm` image is not the production service image.

### Record ownership

The latest atrium-project#73 thread explicitly supersedes the old owner:

- `keyword-extract` owns the new `keywords` block;
- document-level **and per-page** statistical keywords are required;
- statistical and controlled keywords stay in separate lists/fields;
- each keyword keeps method/score/rank;
- document quality summary remains a separate atrium-project#73 concern and must be derived from the existing page/line quality baseline.

### Governance / release boundary

- `atrium-project#71` owns the common seeded record, source identity and `CreateAction` contract.
- `atrium-project#72` owns the one-production-image-per-stage rule, shared LLM/vocabulary governance and image closure.
- `atrium-project#73` owns the record-level discovery outputs; its latest comment makes `keyword-extract` the keyword owner.
- `atrium-digital-convert#1/#2` own the born-digital converter/service work, not keyword extraction.

## ⚠️ Important nuances from the latest work

- **2026-10-07 — one prompt for every path.** The `llm_client_shared.py` that arrived from llm-enrich still sent its own prompt literal: the strict geographic guardrail after #2's M11/M12 relaxed it and reinstated the geographic and cultural terms, no `PROMPT_*` flag, no `teater_category_ids`, and the bracket of a qualified homonym (`zámek (sídlo elity)`) left on the label. It now renders `prompts/system_prompt.txt` through `prompt_template`, like `llm_run.py`, and a test holds its untruncated prompt byte-identical to the committed `prompts/prompt_full.txt`. The clients and the service refuse to run with a guardrail wording the vocabulary contradicts.
- **The record is the input, line by line.** The controlled kind reads the record's `lines[]` (the untrustworthy categories skipped, neighbours as context, the record's page labels cited). llm-enrich's conversion of PDF/DOCX/records to Markdown was digital-convert's converter and stayed there; a `.md`/`.txt` is still read in document mode by the batch clients.
- **Status codes of the controlled kind.** 501 when the deployment has no LLM backend (the 501 of `v1.0.0-beta`, now with the reason), 502 when every call fails, 422 `limit_exceeded` when every reply is cut at `LLM_MAX_NEW_TOKENS`. With `kind=both` none of these costs the statistical keywords: `kinds` says `skipped` or `failed`.
- **Credentials never reach paradata.** The clients and `llm_run.py` logged the whole `llm_config.txt`, which may hold `OPENROUTER_API_KEY` or `HF_TOKEN`; `redact_secrets` drops them (2026-10-07).

- The actual repository name is **`atrium-keyword-extract`**, not the original issue-body spelling `atrium-keyword-extractor`. The service code and `para_config.txt` use `atrium-keyword-extract` / `keyword-extract`.
- The current repository was seeded from **nlp-enrich history**; `llm-enrich` history was not merged as a second full repository history. The code still has the LLM/vocabulary implementation needed for the controlled research path, while `digital-convert` deleted the former `llm-enrich` copy on 2026-10-04 (`20dabd8`). The remaining work is therefore **taking the 24 differing/absent files**, not another repository-creation step.
- The controlled vocabulary work has changed materially since the first split plan. The latest `test` discussion says **4718 terms** are in force, with M11/M12 reinstatement, M13's 7 splits, configurable prompt blocks, collision handling, and a D1 evaluation blocker. This should be treated as current controlled-stage development state, not copied as a frozen final vocabulary claim.
- The current hub E2E already uses the correct new image and route:
  `ghcr.io/ufal/atrium-keyword-extract-api` → `POST /extract_keywords` → statistical smoke with YAKE. It is green since the new packages became readable by the hub (2026-10-05).
- `keyword-extract` should not create a second TEITOK production writer merely because the repository contains TEITOK helper/projection code. The cross-stage ownership remains in `nlp-enrich`; keyword-extract produces the semantic data needed by that projection.
- `YAKE` is **AGPL-3.0**, while the code is MIT and KeyBERT/sentence-transformers/model components carry their own MIT/Apache-2.0 terms. Run-level licence reporting must continue to follow `para_config.txt`; do not collapse the repository licence into the licence of every possible run.
- The current release has **no `keywords` record block**. The presence of a working response with `method`, `score`, `rank`, page lists and paradata is not evidence that the schema work is finished.
